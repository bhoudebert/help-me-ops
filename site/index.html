What an investigation finds

The answer is never in one place.

A customer paid and has no order. The logs show a refusal, the metrics show why, and only the database shows the damage. The assistant crosses them, and tells you what it could not see.

Only a database says it: orders 4512, 4513 and 4514 were captured by the payment provider and are still awaiting_payment. Three paying customers, 165.20 EUR, no order. A log search alone would have stopped at "a webhook failed".

The method

It investigates the way your team does.

Not a chatbot guessing: a loop with guard rails, shared by every client.

Scope first

Apps and environments are explicit. A question about prod is never answered from staging, and when it is unclear, the assistant asks.

Your playbook

Markdown runbooks say what to check, in which order, and what your names mean. They grow after every incident.

Evidence, quoted

Each result has a source and a time. The conclusion quotes them, and never states what no evidence shows.

A checked verdict

Likely cause, how sure, what is unknown, and a next step for a person. Every quote must be a line a tool returned: an invented one is refused. Nothing is changed for you.

Under the hood

A playbook is a Markdown file. Nothing more.

It is the page your team would hand to whoever is on call: when it applies, and what to check, in order. No schema, no code. The assistant reads it as written and follows it before it improvises. Grown after every incident, it is how your team's experience stays in the tool.

playbooks/order-stuck.md---
name: Order stuck or missing
when: a client cannot find their order,
      paid but no order, order not confirmed
---

1. The order itself. order.getOrder
   Its status and when it last changed.
   awaiting_payment -> confirmed -> shipped

2. Its story in the logs. searchSource
   Search app-logs for the number. The event that
   moves an order is "webhook payment.succeeded".
   If it never arrived, who refused it?

3. What it waits for.
   health.checkHealth: is it us or the provider?
   metrics.queryMetric: queue depth, memory.

4. Others affected. order.listOrders
   One order, or all of them?

5. Conclude with the cause, how sure you
   are, the evidence, and what is unknown.
   The fix is for a person.
  1. A problem is reported"Client u-881 paid but cannot find order 4512."
  2. The playbook is foundlistPlaybooks matches the words of when (paid, order, find) with the question. It ranks, it does not guess.
  3. It is read as writtengetPlaybook hands the text to the assistant. Your names, your order, your warnings.
  4. Each step becomes a tool callThe steps name the addons and sources to use, so the assistant looks where your team looks, with the scope you set.
  5. Gaps are said out loudA step with no source behind it ends up under "unknown" in the conclusion, never as an invented fact.

No playbook fits? It investigates from the tools alone, with fewer guard rails. Addons can ship their own playbooks too. Write a playbook. What your team knows (runbooks, past incidents) goes in a knowledge/ folder, searched by words and quoted like any other evidence: write down what you know.

Plug in anything

Two files. No MCP. No AI knowledge.

An addon teaches help-me-ops to read one more place. Describe it in a manifest, write plain functions, drop the folder in. The tool is served to every client, for each environment, always read-only. It can also say what is personal in its own domain, a company id with its check digit for instance, and the mask will hide it everywhere.

addons/billing/addon.json// what it offers
{
  "apiVersion": 1,
  "settings": {
    "dbUrl": { "type": "string", "secret": true,
              "env": "BILLING_DB_URL" }
  },
  "tools": {
    "getInvoice": {
      "description": "One invoice: status, amount",
      "params": { "id": "string" }
    }
  }
}
addons/billing/tools.ts// what it does
import pg from "pg";

export async function getInvoice({ id }, { settings }) {
  const db = new pg.Client(settings.dbUrl);
  await db.connect();
  const { rows } = await db.query(
    "SELECT * FROM invoices WHERE id = $1", [id]);
  await db.end();
  return rows; // the assistant quotes these
}
$npm run ops -- init addon billing --template sql  # or file, api: a working addon with TODOsnpm run ops -- addon check addons/billing  # ok / warn / FAIL, each with its fix

Trusted with production

Read-only is not a promise. It is layers.

The assistant can only ask questions. Each layer below refuses a write on its own, so a mistake in one is caught by the next.

  • Declared and tested

    Every tool says it cannot change anything, and a test checks it. No tool can write.

  • Fenced in

    Allow-listed paths, parameterised queries, no redirects, capped answers. Secrets never reach an error message.

  • Your accounts decide

    A SELECT-only database user, a read-only token. Even a buggy addon cannot go further.

  • No keys, no bill

    The model is your client's, on your subscription. This project makes no model calls and stores nothing.

  • Your data goes where your client sends it

    What a tool returns reaches your AI provider. List the fields and patterns to hide in ops.config.json, or let an addon declare its own (a company id with its check digit): a safeguard, not a guarantee. Expose only what an investigation needs, or use a local model. Personal data.
